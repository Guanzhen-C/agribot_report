# 部署与故障排除

## 分层检查

先区分“应用打不开”“ROS任务没起”“传感器无数据”“定位未就绪”“规划失败”“底盘未接管”，不要把所有问题都归为网络。

| 现象 | 首要检查 |
| --- | --- |
| Unity编译模型资源错误 | doctor --unity、Git LFS、授权资源、Editor版本 |
| 按启动后Gazebo/RViz没出现 | 本次受管任务日志、增量构建结果、DISPLAY与GL环境 |
| 相机No Image | 图像topic、QoS、Gazebo渲染环境、视觉AI是否启动、真实相机触发状态 |
| 模型红色/无材质 | MTL和贴图相对路径、资源是否完整，不把错误材质当传感器检测结果 |
| 车原地不动 | 目标是否提交、定位/TF、Nav2生命周期、路径、速度门控与运动学约束 |
| 到点后绕圈 | 激活goal checker、容差、目标是否更新、是否启动了旧进程 |
| RTK初始化长期等待 | 质量、航向、地图地理参考、粗先验、3D配准日志 |
| 车周围假障碍 | 车体/支架自反射、高度带、坐标变换、旧障碍清除；不能盲删真实障碍 |
| 手机状态低频或断连 | HTTP可达性和车端负载；前端消息频率不当成传感器采样率 |
| AI无回答 | 私人Key/模型名/网络、超时、本地校验错误；手动流程仍可用 |

## 日志与状态

ROS构建日志在交付工作区 `ros2_ws/log/`，运行日志通常在ROS日志目录和各任务状态目录。Unity助手会话日志在Unity persistentDataPath的 `assistant_sessions`，属于用户数据，不入Git。构建输出在 `dist/`，本次交付检查输出在 `.validation/`。

```bash
source scripts/env.sh
ros2 node list
ros2 topic list
ros2 action list
ros2 lifecycle nodes
```

真实传感器频率应在车端就地测量，避免跨不稳定Wi-Fi用高带宽订阅得出错误结论。检查处理延迟时同时考虑header时间、接收时间、设备时钟映射和周期配对，不以“显示延迟接近零”证明已做真实硬件时间标定。

## 时间同步

代码包含RTK TTL+PPS授时、C16 gPTP与PPS相位、相机触发和IMU设备时间映射等硬件适配。具体接线、引脚复用和是否持续硬件锁相取决于板卡/已安装模式，不能把历史pin配置通用于任意平台。室内GNSS失锁、冷启动尚无绝对时间、pps保持与系统时钟保持是不同状态，应分别诊断。

不开车进行同步/驱动测试。禁止为了让诊断变绿，单纯把接收时间替换成触发时间而不建立可信帧对应关系。实际曝光、扫描方向、整帧头和每点时序是不同概念。

## 真机安全检查

默认CAN输出关闭。检查车辆尺寸和定位、障碍、规划后再授权，现场急停有效，遥控模式正确，先低速空旷测试。仿真机具无碰撞是展示策略，真实安装后必须重新评估突出部分和安全间距。

控制台网络仅用于任务/状态，不应承担定位闭环。不要向互联网直接暴露未认证HTTP网关；要远程使用应另设安全隧道、认证和权限。

## 数据与升级

不把开发机build/install复制到不同架构；从源码重新构建。升级前记录当前提交和配置，保留地图、地理参考、视觉库以及用户导出文件。先停受管任务再升级，不在导航中更换外参或替换地图。

录包停止并确认收尾后再卸盘。源扫描文件与转换缓存分离，删除导入场景只删缓存；原始实验数据不作为Git仓库内容。不要运行大范围 `killall`、`git reset --hard` 或目录清空来替代正常停止。
