# 架构与数据流

## 配置到仿真

```text
Unity 车库/装备/参数/场景/算法
    -> VehicleConfiguration 导出 JSON + OBJ/MTL
    -> unity_sync_and_simulate.sh
    -> agribot_vehicle_config_tools 校验/生成
    -> generated/<vehicle_id> 的 URDF/SDF/YAML/manifest
    -> configured_ackermann_sim.launch.py
    -> Gazebo 虚拟传感器 + ROS 定位/规划/控制
    -> RViz 地图/模型/图像/轨迹
```

名称虽含 ackermann，统一 launch 根据配置中的运动学处理多车型。不能仅凭文件名判定履带车也使用阿克曼约束。

脚本对模型和算法先校验/准备，再替换它管理的上一个仿真，不使用全局 killall 清理别人的 ROS 任务。启动失败应读取本次运行日志，不重复点击启动堆积任务。

## 真机闭环

```text
C16 点云 + IMU + 相机
    -> 时间戳/必要过滤 -> FAST-LIVO2 -> 连续局部里程计
RTK 固定解位置 -> 因子图融合/全局约束
地图 + RTK/视觉/手动粗位姿 -> 两级 NDT + GICP 初始配准
    -> map / odom / base_link 坐标链与定位就绪状态
静态二维地图 + 实时障碍 -> Nav2 costmap
Nav2 目标/经停点 -> 全局规划 -> 局部控制 -> 速度安全门控
    -> 对应车辆 CAN 驱动 -> 底盘控制器
```

RTK 粗初始化和运动中固定解融合不是同一个验收条件：浮点航向允许用于粗先验，不意味着浮点位置进入强位置因子。最终以 `rtk_map_initializer.yaml`、`fastlivo_rtk_fusion.yaml` 和实际驱动状态为准。

传感器接收和计算采用分组/后台线程及有界缓冲等适配；“有多线程”不保证任意资源负载下实时。队列长度、时间戳和处理滞后仍须检查。

## 控制台

```text
Android 内置前端 / 浏览器
    -> HTTP JSON 请求 + 状态事件
    -> agribot_mobile_app 网关
    -> ROS Action / Topic / 受控进程任务
    -> 原有车辆 launch 与算法
```

手机不承担实时传感器融合或车辆运动控制循环。退出页面不应切断定位节点。网络断开会影响状态和指令传达，安全停车策略应在车端而不是浏览器计时器中实现。未经隔离的 DDS 高带宽图像跨 Wi-Fi 可能拖累系统，默认本地 ROS 图和 HTTP 状态发布用于避免此问题。

## 两种 AI 功能不要混淆

1. Unity AI 助手：自然语言 + 界面状态/操作 + 当前适配目录，输出聊天、备忘和配置方案；只读工具 `list_scenes` 查询真实场景目录；本地校验后由用户应用方案，用户另点启动。
2. 真机语义导航：服务器检索语义图/图数据库、解析目的地与禁行要求，再向 Nav2 发送经过校验的目标。与 Unity 装配推荐不是同一个提示词、接口或执行器。

AI Key 不编译进 App。场景目录版本未变时复用本会话的有效查询结果，减少重复模型请求；结构错误有界重试，不能无限生成，也不能绕过本地约束。

## 固件边界

HPM6750 是可选 CAN 桥接硬件，不替换 RDK 定位/规划，也不替换底盘 STM32 闭环。上位机源码保留于固件子目录供参考，当前移动控制台已经有自己的网关与界面。固件由人工选择正确板卡/协议后烧录，不在手机点击导航时自动刷写。
