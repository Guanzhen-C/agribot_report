# 架构与数据流

## 总体流程

```text
Unity 选车/装配/参数/场景/算法
    -> 当前车辆 JSON 与 OBJ/MTL 导出
    -> unity_sync_and_simulate.sh
    -> agribot_vehicle_config_tools 校验/生成
    -> generated/<vehicle_id> 的 URDF/SDF/YAML/manifest
    -> configured_ackermann_sim.launch.py
    -> Gazebo 虚拟传感器
    -> 定位 -> Nav2 规划 -> 局部控制 -> 仿真车辆
    -> RViz 显示与人工任务输入
```

统一 launch 根据车辆配置选择运动学，名称含 ackermann 不代表履带车也用阿克曼模型。

## 配置层

Unity 负责可视配置和导出。Python 生成器统一校验单位、尺寸、传感器位姿、运动学和模型引用，生成仿真使用的文件。不能只修改某一个 URDF 而不同步 JSON 和其他参数。

配置指纹关联当前模型和验证记录；旧指纹的通过标签不能自动用于修改后的模型。

## 仿真层

Gazebo 发布相机、激光、IMU、模拟 GNSS 与车辆状态，ROS 使用仿真时钟。不同定位组件以统一位姿/里程计接口接入导航。全局规划和局部控制按照所选组件及车辆几何配置运行。

FAST-LIVO2+RTK、NavSat 等实现复用共享包。保留这些源码是为了闭合仿真依赖，不是附带交付控制台或真机应用。

机具保留可视和惯性，运行时临时模型去除其碰撞；本体和轮地接触仍保留。该策略不等于物理机具安全验证。

## 进程管理

启动脚本先校验、导入和准备本次配置，再替换它管理的旧仿真。停止操作只针对受管任务，不用全局 killall 清理其他项目。普通启动不自动发送目标，车辆等待用户在 RViz 指定。

## AI 层

Unity 将文字对话、当前选择、近期操作与会话备忘交给 Python 后端。后端生成当前车型/机具/场景/算法知识，调用模型并校验结构化结果。用户点击方案后应用配置，之后仍需单独启动仿真。

唯一只读 Function Call 是 list_scenes({})。目录版本未变时复用本会话有效摘要；导入、删除、目录变化或新会话使其失效。没有导入、启动、运动控制或任意文件执行工具。

助手不接收相机图像、点云或实时定位质量。文字名称不能替代场景语义识别。凭据只在工作站私人配置中读取。
